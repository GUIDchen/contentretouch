# 两个坐标口径的翻案：为什么「验证通过」的功能其实一直打错地方

> 这份文档记的是本轮最值钱的发现：**不是功能没做，是做了但落在错误的位置，而当时的验证是循环验证**。

## 一、面部关键点：相对人脸框，不是「图像归一化」

`VNFaceLandmarkRegion2D.normalizedPoints` 是**相对人脸框**的，原点左下、与 Core Image 同向。

老代码写的是：
```swift
CGPoint(x: p.x * W, y: (1 - p.y) * H)      // ❌ 错
```
正确写法：
```swift
CGPoint(x: box.minX + p.x * box.width,     // ✅
        y: box.minY + p.y * box.height)    // 不翻 y
```

**判定证据**（coretest 第 1 节，几何自证，不依赖蒙版）：

| 图 | 人脸框 | 眼睛质心 | 嘴质心 | 结论 |
| --- | --- | --- | --- | --- |
| 大脸图 600×900 | 490×490 @(43,290) | (292,641) | (285,425) | 都在框内、嘴低于眼 ✅ |
| 婚礼照 1080×1620 | 159×159 | (385,1236) | (383,1174) | 同上 ✅ |

用老口径算，嘴会掉到脸框外（叠加图：`docs/shots/关键点口径校准.png`，红=老口径、绿=正确口径、黄=人脸框）。

## 二、位图蒙版不需要翻 y

老代码在画蒙版处写了 `cy = H - y`，注释说「CGBitmapContext 位图相对 Core Image 垂直镜像」。
实测（coretest 第 2 节）：把一个已知位置的矩形通过 CGContext 画成蒙版，再看这个位置的蒙版值：

    矩形中心处蒙版值：不翻 y = 1.000，翻 y = 0.000
    镜像位置的值：    不翻 y = 0.000，翻 y = 1.000

**结论：CGContext 的 y 与 Core Image 的 y 同向，不需要翻。** 老规矩 8 已作废。
受影响并已修的地方：污点修复笔刷蒙版、全身美型腰部蒙版。

## 三、为什么两个 bug 都能「验证通过」

当时的验证是这样写的：

> 用蒙版采样「嘴内」和「嘴外」，嘴内变了、嘴外没变 → 功能正常 ✅

问题在于：**采样点是用同一个错蒙版算出来的**。蒙版落在哪，采样就在哪，永远自洽 —— 这是循环验证，
不是验证。三个真 bug 全是从这个缝里漏过去的。

## 四、换成的判据（现在的做法）

1. **目标位置来自独立来源**：人脸框/关键点，而且关键点本身先被几何校验过（在框内、嘴低于眼）。
2. **能证伪的口径**：变化质心「离目标近」**且**「离镜像位置远」——镜像正是那两个 bug 会产生的落点。
3. **合成图判据**：查笔刷落点时用「灰底 + 已知位置的黑块」，判据唯一，不受画面内容干扰。
   实测：笔刷点 (110,130) → 变化质心 (109,130)，**距 0.7 px**（镜像位置差 139 px）。
4. **全分辨率比较差异**：缩放比较时 Core Image 的重采样会造出满图假差异（把 5e-6 的真平均差放大成 0.03），
   差一点又误判一次。
5. **还要断言「能出图」**：非整数 extent 会让 `createCGImage` 静默失败 —— 数字好看但导不出图，不算通过。

## 五、可以直接复用的两条工程结论

- **交互落点一律存归一化坐标（0~1）**：预览用 1400 px 工作图、导出用原分辨率，存像素就会整体偏掉。
  半径按「长边百分比」存，同理。
- **关键点检测怕缩图**：1712×2284 缩到 750×1000 后关键点从 1 个变 0 个（人脸框还能检到）。
  `detectFaceGeos` 因此内置小脸回退：先检框 → 把脸附近裁出来放大到 ≥640 px 再跑一次 → 坐标映射回来。
