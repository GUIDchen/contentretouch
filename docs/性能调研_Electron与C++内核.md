# 性能调研：要不要换 Electron / C++ 内核（2026-09）

结论先给：**都不需要**，而且是**用实测数字否掉的**，不是靠直觉。

- 换 Electron：像素运算慢 **8~15 倍**，并且要放弃 Vision + CoreML 这套 AI 能力（整个产品的差异化）。
- 换 C++ 内核：**没有收益可抢**——整套像素链（模糊+锐化+全分辨率回读+JPEG 编码）只占 **8.5 ms**，
  而一次人脸解析要 **96.7 ms**。把 8.5 ms 优化掉一半，也就是总耗时的 **0.9%**。

## 一、方法：先解决「测量本身是错的」

Core Image 是**惰性求值**的：写 `img.applyingFilter(...)` 不产生任何计算，真正算是在最后回读/渲染时。
我第一次按阶段计时，得到的是「补光 0 ms、锐化 0 ms」，全部成本都掉进了最后一步 —— 这种数据会把人带偏。

这次的两种测法：

1. **强制求值**：每步结果渲染到 32x32 的小图（成本极低，但会触发整条图求值），从而把「这一步的边际成本」量出来。
2. **端到端**：像素链 + 全分辨率回读 + JPEG 编码一起量，这才是导出真正要付的钱。

样本：抖音素材库 20~24 张（811x1080，webp 为主），每次取 3 次最小值（避开 Metal 着色器首次编译的抖动）。

## 二、四块耗时（811x1080）

| 环节 | 实测 | 占比（按整条链路 ~465ms） |
| --- | --- | --- |
| 读图 + 解码（webp） | **63.0 ms** | 13.5% |
| 人脸 + 关键点（Vision，首次） | **26.9 ms** | 5.8% |
| 同上（缓存命中） | **14.5 ms** | — （省 46%） |
| 人脸解析（CoreML 512²，一次推理 + 建掩膜） | **96.7 ms** | 20.8% |
| 解析掩膜（坐标映射 + 羽化） | **71.3 ms** | 15.3% |
| **像素链（高斯 r=28 + 锐化）+ 全分辨率回读 + JPEG 编码** | **8.5 ms** | **1.8%** |

> 一眼就能看出问题：**一次模型推理 96.7 ms，整套像素运算连回读带编码 8.5 ms**。
> 差了一个数量级。要提速只能从模型和解码下手。

## 三、三条像素路径实测对比（720x1080）

| 路径 | 3x3 锐化 | 盒式/高斯模糊 r≈28 |
| --- | --- | --- |
| **vImage（Accelerate，C 向量化）** | **0.5 ms** | **2.2 ms** |
| **Core Image（Metal，现在用的）** | ~1 ms | ~2 ms |
| **纯 JS 单线程（Electron 的极端情况）** | **7.6 ms** | **18.8 ms** |

读法：

- **C/C++ 路径（vImage）和我们现在的 Metal 路径基本打平**（0.5/2.2 vs 1/2 ms）。
  也就是说：手写 C++ 内核**最多也就是追平现状**，不可能带来数量级收益 —— 因为这块本来就已经是向量化的了。
  而且现在的 Core Image 是**惰性图**：挪动滑杆时十几个滤镜会合成一次求值，中间不回读；换成 C++ 要自己维护这层融合，费力且多半更慢。
- **JS 路径慢 8~15 倍**。注意这已经是很客气的估计：
  纯 JS 循环是下限，实际 Electron 会用 WASM/WebGL，但即便如此也追不上 Metal，
  而且 Electron 里**没有 Core Image 这样的滤镜图**，也没有 **Vision / CoreML**。

## 四、Electron 的真实代价（结构层面）

| 维度 | 现在（原生 Swift + SwiftUI + Core Image） | 换 Electron |
| --- | --- | --- |
| 像素运算 | Metal，8.5 ms 全链路 | JS/WASM 慢 8~15 倍 |
| AI 能力 | **Vision**（人脸/关键点/显著性/实例分割/姿态）+ **CoreML**（人脸解析/SAM） | **全部没有**，得换成 ONNX/WASM，公认慢一个档 |
| 运行时体积 | 安装包 **18 MB** | Chromium + Node 起步 **150~250 MB** |
| 内存 | 实测常驻 **~143 MB** | Electron 空载通常 200+ MB |
| 系统集成 | 取景框/菜单/快捷键/文件面板都是原生 | 需要额外桥接 |

> 这个 App 的核心价值恰恰在 Vision + CoreML 那一层（皮肤/唇/眼/口腔语义掩膜、SAM 精细分割、
> 场景识别、姿态分级），换成 Electron 等于把最值钱的部分推倒重来，而且是换成更慢的实现。

## 五、那真正该优化什么（按实测收益排序）

| 方向 | 依据 | 预期 |
| --- | --- | --- |
| 少调模型 / 显式传参 | 批处理里解析被重复调用（缓存命中率只有 29%） | 每张能省 70~100 ms |
| 交互场景的缓存 | 同图反复调参命中 75%，21 → 15 ms/次 | 已经做了 |
| webp 解码 63 ms | 占 13.5%，且每张都要付 | 可以用缩略图预览 + 导出时才全解码 |
| 尾延迟（多脸） | 9 张脸那张 8.3 s | 限制重活只做够大的脸 |
| 模型可选下载 | 已在 SAM 上验证：安装包 41 → 18 MB | 人脸解析也能再省 12.7 MB |

## 七、附：本轮据此做的优化（2026-09，实测）

调研结论落在「少调模型、别在全分辨率上跑掩膜」，实测做了两件事：

| 改动 | 效果 |
| --- | --- |
| 按脸解析缓存（同一张脸只推理一次） | 7 张脸的图：牙齿 596→**38 ms**、眼睛 564→**40 ms**，整组 864→**71 ms** |
| 大图跑掩膜前降到 ≤2048 + 掩膜羽化改到放大前 | max **8287 → 5238 ms（−37%）** |

同一批 667 张（抖音库）同口径：p50 670→**626 ms**、p95 2016→**1910 ms**、成功率仍 667/667。

> 仍然最慢的是 **32.6 MP** 的那张（6998x4665，5.2s），其中 JPEG 编码（32MP）就占 1.07s —— 这是像素数的固有成本，
> C++ 内核也省不掉（编码是 libjpeg-turbo 的活，Apple 的 ImageIO 已经在用它）。

## 八、解码与编码：又测了一轮（2026-09）

顺着「C++ 能不能帮上忙」这个问题，把编解码也量了一遍（它们比像素运算贵一个数量级）：

| 方案 | 实测（同输出尺寸） |
| --- | --- |
| webp 解码 | **82.5 ms/张** |
| jpg 解码 | **23.1 ms/张** |
| webp 走 ImageIO 缩略图解码 | 83.1 ms（**没收益**） |
| jpg 走 ImageIO 缩略图解码 | 21.1 ms（省 9%） |
| 解码缓存命中（内存/磁盘） | **1.9 ms/张** |
| 导出 JPEG 21.3MP（CGImageDestination） | 83 ms |
| 导出 JPEG 21.3MP（CIContext 直编） | **45~61 ms** |

结论：
1. **webp 解码慢是格式本身的代价**（3.5× jpg），换解码 API 无用——缩略图解码对 webp 完全不生效。
   能做的只有「别重复解码」（缓存），实测 152.6 → 1.9 ms。
2. 导出那条路**确实能省**：`CIContext.writeJPEGRepresentation` 直接从 GPU 链编码，
   省掉「回读成整张 CGImage」这一步——这属于「换实现」而不是「换语言」。
   用 C++ 重写 JPEG 编码只会更慢：Apple 的 ImageIO 底下已经是 libjpeg-turbo 那类优化实现。
