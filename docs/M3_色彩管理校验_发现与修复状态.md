> ✅ 结论：**根因找到并修好了**。不是色彩空间、不是编码、不是 Core Image —— 是我自己代码里三行放错位置。
>
> 根因（retouch-cli/main.swift）：本图自适应那三行**写在了 identity 判断之外**，于是恒等自检也被加了
> `brightness +5`。Core Image 里 brightness 是加性偏移，5/100 = 0.05 ≈ **+12.75 级** —— 正好就是量到的「亮 13 级」。
>
>     let over = max(0, s0.p50 - 120)
>     p.gamma = max(1.0, p.gamma - over * 0.001)
>     p.brightness = max(0, 5 - over * 0.10)      ← 这段跑在了 identity 分支外面
>
> 修法：整段包进 `if !identity { ... }`。
>
> 修好后的实测：恒等往返 源 73.29 → 出 73.30（RMSE 0.005，基本无损）；三张全部一致。
>
> 教训（写进注释了）：自检开关必须把**所有**会影响像素的代码都挡住；打印参数时也要把 brightness 一起打出来，
> 否则「看起来是恒等」但实际不是。

## （以下为最初的排查记录）

> 复查清单第 4 条写着「色彩管理最容易悄悄偏色，必须做一次像素级校验」。
> 做完校验之后，它确实抓到了一个真问题——而且是会直接影响出片的问题。

## 1. 怎么验的

给命令行加了 `--identity`（恒等参数：色阶不改、gamma 1、不降饱和、无分色调），然后拿它出的图和原图逐像素比。
恒等渲染「应该」等于原图（只差编码噪声）。

## 2. 结果：不等，而且差得不少

    wedding_01   源均值 73.29 → 出均值 86.21   （亮了约 13 级）
       R: 105.4 → 118.4    G: 58.5 → 71.4    B: 55.9 → 68.8   （三个通道一起抬）
    RMSE 0.0507（每像素都不同，但 std 几乎不变 65.58 → 65.58 → 是整体抬亮，不是对比变化）

另外两张同理（wedding_03 只差 0.002，因为它本身很亮、抬升空间小）。

## 3. 排除法（都是实测）

| 假设 | 验证 | 结论 |
| --- | --- | --- |
| JPEG 编码造成 | 改用无损 TIFF 往返，RMSE 0.0501 | **不是编码** |
| 色阶曲线（CIToneCurve 样条）造成 | 跳过恒等曲线后数值一模一样 | 不是曲线 |
| ICC 剖面不匹配 | 源与出都是 sRGB、都没有剖面 | 不是剖面 |
| workingColorSpace 设成非线性 sRGB | 改成默认（扩展线性）后反而更亮（均值 105.7） | 两种配置都不对，问题在**解码端** |

## 4. 目前判断的根因（尚未修）

`CIImage(contentsOf:)` 读 JPEG 时**没有按 sRGB 给图像打标签**，于是 Core Image 把 sRGB 编码的值当成工作空间的值，
写回 sRGB 时又编码一次 —— **双重伽马**，整体抬亮。

正确修法（已写进代码注释）：改用 ImageIO 读进一张**显式 sRGB 标签**的位图再交给 Core Image：

    CGImageSourceCreateWithURL → CGContext(space: sRGB) → draw → makeImage → CIImage(cgImage:)

再做一次恒等往返，RMSE 应当降到只剩编码噪声（<0.005），那时才算修好。

## 5. 影响面（重要）

- **闭环本身仍然自洽**：测量与渲染用的是同一个空间，所以「误差 1.150 → 0.706」这种**相对**比较有效，逐张自适应也照常工作；
- **但写出的 JPEG 会整体偏亮（约 13 级）**：现在拿它出正式交付件会偏亮，需修好后再用；
- 之前用 Python 验证版的那些结论（Pillow 那条路）不受影响，因为它们走的是 PIL 解码（正确按 sRGB 解释）。
