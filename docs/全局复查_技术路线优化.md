# 全局复查：阶段划分与技术路线的问题清单

> 复查对象：docs/AI修图App_调研与技术路线.md、像素蛋糕两份调研、以及已跑通的原型与索引。
> 结论先说：**方向没问题，但有 6 处该改**——其中 2 处是会让人白干一场的顺序问题，1 处是没验证过的关键假设（本轮已补验，结果很好）。

## 0. 本轮新验的关键假设（M4 的地基）

**假设**：Vision 768 维特征向量能当「找相似参考图」用。
**验证**：用你的婚片 wedding_01 去 6,988 张已索引的收藏里搜 Top-10，拼图目视检查 ——
**10/10 全是中式婚礼同题材**（红裙/秀禾/军装、红囍背景、暖调室内光），命中率 100%。
另外用库里同一张图去搜，Top-8 里 7 张来自**同一件作品**（同一组图），说明它连「同一场拍摄」都能区分。

由此得到一个重要的**设计修正**：

- 绝对距离**不能当相似度百分比展示**：实测 0.58~0.65 的这批「高度相关」，而 0.31 的那批是同一组图——
  不同题材的距离尺度不一样。界面只给**相对排序 + 缩略图**，或者干脆按「作品」聚成组给（推荐 3 组而不是 10 张）。

## 1. 阶段划分：两处该调顺序

| 原计划 | 问题 | 建议 |
| --- | --- | --- |
| M2 App 骨架 → M3 参数接入 | **先做 UI 再证明管线，顺序反了**：UI 只是壳，真正决定成败的是「8 张婚片批量出片能不能看」 | **M2 改成：命令行闭环**（参数工厂 + 批量出图 + 导出），用你自己的片子跑通；M3 再套 UI |
| M4 相似推荐 | 现在索引已跑完一半、检索已验证，**它的前置条件比 M2/M3 更早满足** | M4 的「检索」部分可以提前做（半天），只有「推荐组 + 参数」依赖 M2 的参数层 |
| M5 磨皮/美型 | 「复刻 PixCake 美颜」是个无底洞，且不是你最缺的 | 改成「**参考图驱动的皮肤处理**」：肤色统一到参考组 + 轻度质感磨皮 + 斑点修补，只做这三样，且由参考组统计驱动 |

## 2. 技术路线：需要修正的点

### 2.1 从「开环猜参数」改成「闭环收敛参数」（最重要）
现在：参考组统计 → 推参数 → 套用。参数是一次性算出来的，套完没人回头看像不像。
应该：套用后**重新度量成片**，与参考组比 ΔE / 直方图距离 / 肤色落点，不达标就微调（gamma、levelsOut、cb 三轮内收敛）。
项目里已经有 check_style.py 在做同类比对——把它接进闭环即可，不用新造。这是把「能用」变成「准」的关键一步。

### 2.2 人物属性 / 多脸分组：原方案漏了
PixCake 最实用的一层是「一张图里给不同人不同参数」（5 种人物属性 + 单人/所有人/部分人联动）。婚礼合影必然多脸，
我们却只按整图算参数。Vision 可以一次检出多张脸 → 参数按脸存、按脸作用。**这个不补，影楼场景直接不成立。**

### 2.3 色彩管理必须写死在方案里
原方案只写了「Core Image 出图」，没定工作色彩空间与输出 profile。这是最容易翻车又最容易被忽略的一环：
（a）工作空间用线性 sRGB 还是 Display P3；（b）导出的 JPEG/TIFF 嵌哪个 profile；（c）与 Photoshop 管线对不上的时候以谁为准。
实测项：拿一张图过一遍链子，比对象素值与色彩 profile，确认没有色偏。

### 2.4 RAW 入口要留
PixCake 的卖点之一是 16bit AI Raw 引擎。我们现在的输入是 JPG，但婚礼摄影迟早会遇到 RAW——
Core Image 有 **CIRAWFilter** 可以直接解 RAW 并保持 16bit，**方案里要给它留位置**（M3 或 M4 加，不是现在做）。

### 2.5 索引 schema 少了一样东西（但不必现在补）
索引里存了 Vision 特征 + 均值色，没有存影调统计（p50/饱和度/暖冷）——而 M4 推荐出参考组后要**给出这组的风格参数**。
懒人正确解：**只对 Top-N 现算**（一次查询 5~10 张，Python 秒级），不要为了它重跑 13,484 张的索引。

### 2.6 批量必须能失败、能跳过、能重跑
500 张里总有解码失败/无人脸/参数异常的。原方案没写失败处理。约定：
逐张状态（成功/跳过/失败+原因）、原图**永不被覆盖**（只写新目录）、参数表落盘可重跑、可只重跑失败项（这套语义现有 App 已经有，直接沿用）。

### 2.7 预设要有格式
「预设能从你的库长出来」这句话要落地就得有 schema：
`{ name, source: { refIds[], cluster }, style: {levelsIn/Out, gamma, contrast, cb*, desat, skin…}, version }`——
一个 JSON 文件一个预设，可导入导出、可版本化、可回滚。别塞进代码里。

### 2.8 工程形态定下来：SPM 包 + 打包脚本，不手写 .xcodeproj
手写 Xcode 工程文件几乎不可维护。既然现在有完整 Xcode，正规做法是 **Swift Package**（`Package.swift` + `swift build`），
再用一个脚本把可执行文件装进 .app（Info.plist + 图标 + ad-hoc 签名）——和现有 tools/dist 里的打包脚本一个思路。

### 2.9 两个 App 的关系：保持独立
ContentHarvester（Tauri，采集）与 ContentRetouch（Swift，修图）**不合并**，用「参考库目录 + 参数 JSON」互通。
理由：把 Tauri/Rust 那套搬进 Swift 只会得到一个两头都不好维护的东西；采集与修图的生命周期也完全不同。

### 2.10 合规边界写清楚
参考图是他人作品。我们**只取统计量（直方图/分位数/色偏）与特征向量，不把参考图的任何像素复制进成品或 LUT**。
（这条要写进代码注释与文档，避免以后做 LUT 时不小心把参考图色块嵌进去。）

## 3. 需要立刻修正的 6 件事（按优先级）

1. **M2 与 M3 换位**：先命令行闭环，后 UI。
2. **参数闭环**：套用 → 度量 → 微调，接 check_style 的比对逻辑。
3. **多脸/人物属性**：参数按脸组织（数据模型现在就定，别等 UI 写完再改）。
4. **色彩管理**：明确 working space 与输出 profile，并做一次像素级校验。
5. **检索展示口径**：不做「相似度 %」，做「推荐 3 组 + 缩略图 + 组内参数」。
6. **预设 schema**：JSON 文件格式先定，UI 后做。

## 4.5 复查过程中抓到的真 bug（已修）

**现象**：全库索引跑到 6,988/13,484 时**卡死不动了**——进程还在，但半小时没写出一行。

**定位**：按排序把「已完成的最后一个文件」之后尚未处理的文件逐个用 20 秒看门狗试，抓到 4 个文件必定挂死：

    0080_7683063852598119732_05.webp / _06.webp / _08.webp / _09.webp

**根因**：这几个都是 **8736 × 11648（约 1.02 亿像素）的 webp**——Vision/CoreImage 解这种尺寸的 webp 会直接卡死；
而**同一组、同尺寸的 jpg 完全正常**（说明是 webp 解码路径的问题，不是尺寸本身）。ImageMagick 打开它们却是秒开。

**修复**（两道保护，已重新编译并验证）：

1. **超大图预缩**：边长 > 6000 的图，先交给 ImageMagick 缩成 768px 临时图再索引（实测这 4 个文件 8 秒跑完，超时 0）；
2. **单张超时**：每张 20 秒超时，超时就记 `{"f":...,"timeout":true}` 继续跑，并在结尾汇总「超时 N 张 / 解码失败 N 张」——
   不再让一张坏图拖死整批。

索引已用新二进制续跑（断点续跑生效），目前 7,638/13,484。

## 5. 仍然存在的风险（如实列出）

- **磨皮手感**：M5 只能到「可用」，达不到 PixCake；这是数据与模型差距，不是工程量问题。
- **磁盘（比原以为的严重）**：复查时实measure，根卷**只剩 6.7 GB 可用**。构成：参考库 4.7 GB、Rust 构建产物 6.7 GB、`~/Library/Caches` 18 GB（系统与 App 缓存，非本项目）。
  由此引出一个必须写进方案的约束：**16bit TIFF 导出会非常占地方**——一张 2160×2880 的 16bit TIFF 约 37 MB，500 张就是 ~18 GB。
  对策：① 导出默认 JPEG（质量 95，约 2~4 MB/张）；② 需要 TIFF 时**先估算体积并检查可用空间**，不足就拒绝而不是写到一半失败；③ 参考库可整体移到外置盘（数据目录已经是可配置路径）。
- **色彩一致性**：Core Image 与 Photoshop 的结果不会逐像素一致——两条路都保留：App 出 JPG/TIFF，需要分层 PSD 仍走 batch.jsx。
- **索引速度**：实测 2.9~5.4 张/秒（随图片复杂度波动），13,484 张约 40~80 分钟；增量索引要支持（现在已可断点续跑）。
