# 分发与签名指南（T8）

> 目标：把 App 从「本机 dev 可跑」推进到「别人能装、Gatekeeper 不拦」。
> 结论先给：**本机没有 Developer ID 证书，也没有公证凭据，因此签名与公证这两步无法在此机器上真正执行**——本文把能做的（图标、打包、entitlements、脚本、验证）做完，并把需要证书的步骤写清楚。

## 1. 本机实测环境

| 项 | 实测 | 影响 |
| --- | --- | --- |
| 签名身份 | security find-identity -v -p codesigning -> 0 valid identities | 无法签名，只能出未签名包 |
| 公证凭据 | 钥匙串无 AC_PASSWORD，~/.appstoreconnect/private_keys 不存在 | 无法提交公证 |
| 打包工具 | iconutil / sips / codesign / xcrun / hdiutil / pnpm / cargo 均在 | 本地能出 .app 与 .dmg |
| Tauri CLI | 已装 @tauri-apps/cli 2.11.4（pnpm add -D） | 可执行 pnpm tauri build |

## 2. 已经做完的部分

### 2.1 正式图标

- 用 magick 生成 1024x1024 RGBA 源图（蓝紫渐变圆角底 + 白色下载箭头）
- 派生 Tauri 需要的一组：icon.icns、32x32.png、128x128.png、128x128@2x.png、icon.png
- icon.icns 由 iconutil 生成（89 KB，ic12 类型）
- tauri.conf.json 的 bundle.icon 指向这一组

### 2.2 打包配置

- bundle.targets: app + dmg
- bundle.macOS: minimumSystemVersion 11.0、hardenedRuntime、entitlements 指向 entitlements.plist
- signingIdentity 不写死：只有在环境变量 APPLE_SIGNING_IDENTITY 存在时才注入，避免没有证书时构建失败

### 2.3 entitlements.plist

App 需要拉起外部进程（浏览器、node、ffmpeg、magick）并加载动态库，所以开了：

- com.apple.security.cs.allow-jit
- com.apple.security.cs.allow-unsigned-executable-memory
- com.apple.security.cs.disable-library-validation
- com.apple.security.cs.allow-dyld-environment-variables
- com.apple.security.network.client

注意：这些是为了让「外壳 + 外部工具」这种架构在硬化运行时下能跑；如果以后改成纯 Rust 实现（不拉外部进程），应该收紧到最小集合。

## 3. 本地出包（不需要证书）

    cd app
    pnpm tauri build

产物：

    app/src-tauri/target/release/bundle/macos/ContentHarvester.app
    app/src-tauri/target/release/bundle/dmg/ContentHarvester_<版本>_<架构>.dmg

未签名的包在别人机器上首次打开会被 Gatekeeper 拦（提示「无法验证开发者」）。自用临时解法：

    xattr -dr com.apple.quarantine /Applications/ContentHarvester.app
    # 或右键 -> 打开（只需一次）

这不能用于分发，正式分发必须走第 4 节。

## 4. 需要证书的部分（本机未执行）

### 4.1 准备

1. Apple Developer 账号（个人版 99 美元/年）
2. 创建 Developer ID Application 证书并导入钥匙串
3. 生成 App 专用密码（appleid.apple.com），或创建 App Store Connect API Key（.p8）

### 4.2 一条命令完成签名 + 公证 + 装订

    DEVELOPER_ID_APP="Developer ID Application: 你的名字 (TEAMID)" \
    APPLE_ID="you@example.com" TEAM_ID="TEAMID" APP_PASSWORD="xxxx-xxxx-xxxx-xxxx" \
      sh tools/dist/sign_and_notarize.sh \
        app/src-tauri/target/release/bundle/macos/ContentHarvester.app \
        app/src-tauri/target/release/bundle/dmg/ContentHarvester_0.1.0_aarch64.dmg

脚本做四件事：codesign（硬化运行时 + 时间戳 + entitlements）-> notarytool submit --wait -> stapler staple -> spctl / stapler validate 校验。
没有证书时会以退出码 3 中止并打印现有身份，不会静默产出「看起来成功」的包。

### 4.3 公证常见坑

- 必须用 App 专用密码，不是 Apple ID 登录密码
- 公证对 bundle 内的可执行文件与 entitlements 一致性敏感：改过 entitlements 必须重新签名再提交
- 公证是异步的，脚本用 --wait 阻塞等待；超时可以稍后用 notarytool log <id> 看原因
- 顺序不能省：先签 App、再公证、最后装订票据；DMG 要单独签一次

## 5. 分发渠道建议

| 渠道 | 可行性 | 说明 |
| --- | --- | --- |
| 官网 / 自建 DMG | 推荐 | Developer ID 签名 + 公证即可，无审核 |
| Homebrew Cask | 可行 | 需要公开仓库与校验和，适合开源 |
| Mac App Store | 不建议 | 下载第三方平台内容属典型拒审理由，且沙盒限制子进程与外部工具 |

## 6. 自动更新（已接通，待托管）

Tauri v2 的 updater 已经接好：静态 `latest.json` 清单 + minisign 签名 + 安装前对更新包验签。

### 6.1 密钥（已生成，务必自己备份）

    ~/.tauri/harvester.key            私钥（权限 600）
    ~/.tauri/harvester.key.password   私钥口令（权限 600，随机 24 字节）
    ~/.tauri/harvester.key.pub        公钥（152 字节 base64，已写进 tauri.conf.json）

公钥同样写在 `app/src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`。**换密钥必须同时换这一处**，否则客户端会拒绝新包（keyId 对不上）。

请把私钥与口令抄进密码管理器：本机磁盘坏了 = 更新通道断了，老客户端只能手动重装新版本。

### 6.2 出一次带签名的更新包

    cd app
    export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/harvester.key)"
    export TAURI_SIGNING_PRIVATE_KEY_PASSWORD="$(cat ~/.tauri/harvester.key.password)"
    pnpm tauri build

产物（`bundle.macOS.createUpdaterArtifacts: true` 打开后自动多出前两个）：

    .../bundle/macos/ContentHarvester.app.tar.gz        ← 更新包本体（updater 吃的就是它）
    .../bundle/macos/ContentHarvester.app.tar.gz.sig    ← 它的签名（构建时自动签）
    .../bundle/dmg/ContentHarvester_<版本>_<架构>.dmg    ← 首次安装用

macOS 上 updater 用的是 **.app.tar.gz，不是 .dmg**：清单里的 url 与签名都必须对这份 tar.gz，指向 dmg 的清单在客户端会验签失败。

### 6.3 一条命令发布

    sh tools/dist/publish_update.sh \
      --artifact dist/ContentHarvester.app.tar.gz \
      --version 0.4.0 --notes "这次改了什么" \
      --base-url https://你的域名/dl/ \
      --upload "rsync -av dist/latest.json dist/ContentHarvester.app.tar.gz 你的服务器:/var/www/dl/"

它按固定顺序做四件事：生成清单 → 本地验签 → 上传（`--upload` 里的命令，任意 scp/rsync/aws/rclone 写法都行）→ 拉回远端清单与本地比对，避免「只传了包没传清单」或「清单还是旧版本」。没给 `--upload` 就只生成并验签，文件自己拷走。

### 6.4 常见托管方式（照抄即可）

**A. 自己的服务器 / 虚拟主机（rsync 或 scp）**

    sh tools/dist/publish_update.sh \
      --artifact dist/ContentHarvester.app.tar.gz --version 0.4.0 --notes "改了什么" \
      --base-url https://你的域名/dl/ \
      --upload "rsync -av dist/latest.json dist/ContentHarvester.app.tar.gz 用户@服务器:/var/www/dl/"

服务端只要是个静态目录（nginx / caddy / Apache 都行）。三个要点：
- 必须能通过 https 访问（Let's Encrypt 免费证书即可）
- `latest.json` 的 Content-Type 要是 `application/json`
- `latest.json` 的缓存时间设短一点（如 60 秒），否则发布后客户端要等一会儿才看到新版本

**B. 对象存储（S3 / 阿里云 OSS / 腾讯 COS / Cloudflare R2）**

    sh tools/dist/publish_update.sh \
      --artifact dist/ContentHarvester.app.tar.gz --version 0.4.0 \
      --base-url https://你的桶域名/dl/ \
      --upload "aws s3 cp dist/latest.json s3://你的桶/dl/latest.json --content-type application/json --acl public-read && aws s3 cp dist/ContentHarvester.app.tar.gz s3://你的桶/dl/ --acl public-read"

（OSS/COS 换成各自的 CLI，参数含义一致。）关键是**清单要能被匿名读取**——客户端不带任何凭据。

**C. GitHub Release + Pages**

GitHub 的 Release 资源地址不好固定，常见做法是：更新包放 Release，清单放 Pages。

    # 1) 更新包作为 Release 资源
    gh release create v0.4.0 dist/ContentHarvester.app.tar.gz --title "v0.4.0" --notes "改了什么"
    # 2) 用 Releases 地址生成清单，再把清单推到 Pages
    sh tools/dist/publish_update.sh \
      --artifact dist/ContentHarvester.app.tar.gz --version 0.4.0 \
      --base-url https://github.com/你的用户名/仓库/releases/download/v0.4.0/ \
      --upload "cp dist/latest.json /path/to/你的用户名.github.io/仓库/ && cd /path/to/你的用户名.github.io && git add -A && git commit -m 'update 0.4.0' && git push"

然后 tauri.conf.json 的 `plugins.updater.endpoints` 填 `https://你的用户名.github.io/仓库/latest.json`。
仓库必须公开，客户端才能匿名下载。

**D. 临时隧道 / 内网（只适合联调）**

地址会变（重启就换），老客户端会找不到清单；只建议用来验证流程，不要作为长期方案。

### 6.5 没有服务器怎么办（三条现实路径）

**a) 有一台常开的机器（Mac mini / NAS / VPS）：用 Caddy 两行搞定**

    # /etc/caddy/Caddyfile（或任意目录下的 Caddyfile，用 caddy run 起）
    dl.example.com {
      root * /var/www/dl
      file_server
      header /latest.json Cache-Control "public, max-age=60"
    }

Caddy 会自动申请并续期 Let's Encrypt 证书，https 直接可用。把 `dist/latest.json` 与更新包 rsync 到这个目录即可。

nginx 对应写法：

    server {
      listen 443 ssl;
      server_name dl.example.com;
      root /var/www/dl;
      location = /latest.json { add_header Cache-Control "public, max-age=60"; }
    }

**b) 没有可用机器：用免费的静态托管（需要注册一个账号）**

- Cloudflare Pages / GitHub Pages：把 `latest.json` 放进仓库，更新包作为 Release 资源（见 6.4-C）
- 好处是免运维、自带 https；代价是要注册账号并把清单放进一个公开仓库

**c) 只有这一台 Mac、也只给自己用：其实可以不做自动更新**

自动更新是「给多台机器、多个用户」准备的能力。单机自用的话，新版本直接双击新 DMG 覆盖安装即可，功能不受影响——App 里的「检查更新」只会在你配好地址后才可用。想省事就跳过这一节，等以后真有分发需求再回来配。

### 6.6 手动生成清单并自检（发布脚本的等价步骤）

    node tools/dist/make_update_manifest.mjs --artifact <...>/ContentHarvester.app.tar.gz \
      --version 0.4.0 --notes "改动摘要" --base-url https://你的域名/dl/ --out dist/latest.json

    node tools/dist/verify_signature.mjs --manifest dist/latest.json --dir dist

第二条会把「清单 → 更新包 → 签名 → 公钥」整条链路验一遍（自检里还有「改一个字节必须失败」「换公钥必须失败」的负例）。发布前跑一次，比等用户更新失败划算。

### 6.7 托管与地址（当前状态：未托管）

**当前的选择是「暂时不做自动更新」**，所以 `tauri.conf.json` 里的 `plugins.updater.endpoints` 是空的：

- 空 = 不检查更新：点「检查更新」会明确提示「还没有配置更新地址」，不会去撞任何域名（这是单机自用的正常状态）
- 新版本照旧**双击新 DMG 覆盖安装**即可，功能不受影响
- 哪天想启用，二选一即可：


- 改 `tauri.conf.json` 的 `plugins.updater.endpoints` 并重新打包（正式做法）
- 或在 App 的「高级 → 更新 → 更新清单地址」里填地址——界面的「检查更新 / 下载并安装」会用它覆盖配置，不用重新打包（适合内网、临时验证或先试后配）

Tauri 只接受 **https** 端点。签名是端到端校验的：托管方被篡改也换不出能装上的包。

### 6.8 客户端行为

- 「高级 → 更新 → 检查更新」：读清单 + 比对版本，只报告，不动 App。
- 「高级 → 更新 → 下载并安装」：下载 → **校验签名** → 替换 App → 自动重启。按钮带二次确认（再点一次才执行），签名不通过会在下载阶段就报错，不会把没验过的包装上去。
- 安装要求 App 跑在**不含符号链接的真实路径**下：从 `/tmp`（macOS 上 `/tmp` 是 `/private/tmp` 的符号链接）启动会直接报 `StartingBinary found current_exe() that contains a symlink`。这是插件的防掉包检查，属正常行为——把 App 放到 `/Applications` 或任意普通目录即可。
- 更新地址也可以在界面上临时覆盖（「更新清单地址」），用于内网或联调。

### 6.9 本地联调：不开 https 或自签证书

updater 默认拒绝 http 端点。要在本机验证整条链路，临时构建一个允许 http 的**测试二进制**（`--no-bundle`，不会进任何产物）：

    cd app
    pnpm exec tauri build --no-bundle --config '{"plugins":{"updater":{"dangerousInsecureTransportProtocol":true}}}'
    cd /tmp/update-serve && python3 -m http.server 8099 --bind 127.0.0.1 &
    app/src-tauri/target/release/content-harvester --check-update http://127.0.0.1:8099/latest.json

`--check-update` 是 App 自带的诊断开关，走的就是界面按钮那条代码路径；加 `--download` 只验签不安装，加 `--install` 会真的装上（**只在 App 包的副本里用**）。

想做「真实 https + 正式构建」的联调，又不想先买域名：用 Cloudflare 的临时隧道即可（无需账号）：

    cd /tmp/upd && python3 -m http.server 8099 --bind 127.0.0.1 &     # 源站
    cloudflared tunnel --url http://127.0.0.1:8099                     # 输出 https://xxx.trycloudflare.com

把清单里的 url 换成隧道地址，正式的 App（严格配置，不认 http、不认自签证书）就能检查、下载并安装。实测过：发现 0.3.2 → 下载 2,920,259 字节 → 验签通过 → 替换 App → 版本变成 0.3.2。
